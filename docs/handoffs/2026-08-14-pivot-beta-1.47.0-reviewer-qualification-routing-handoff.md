## Behavioral guarantees

- Qualification input is only `providerId` plus `modelId`. Renderer cannot
  provide credentials, endpoints, prompts, tools, filesystem access, database
  paths or arbitrary runtime options.
- Main resolves the configured active Provider and secret, runs an exact
  no-tool structured probe with cancellation and fixed ceilings, then validates
  output and measured usage before persisting evidence.
- Evidence expires after 24 hours and is bound to the Provider `updatedAt`
  revision. Provider changes, expiry, corrupt records, budget excess, malformed
  output and timeout all fail closed.
- Routing updates use optimistic revisions. Enabled routes require a qualified
  correctness Reviewer; all roles are distinct from the Worker and each other.
- SQLite schema version 1 is installed transactionally. A partial unversioned
  schema is preserved as a legacy backup and recovered without pretending it
  was valid evidence.
- Production semantic review is composed only from `readQualified()` during
  Runtime startup. Settings changes deliberately take effect on the next
  Runtime and cannot hot-swap a live guarded transaction.
- Renderer revalidates all IPC responses, cross-checks evidence ownership,
  ignores superseded qualification requests and rejects forged routing revision
  or payload responses.
- Worker and Renderer receive no Admin Port, ProviderStore, secret reader,
  SQLite handle, qualification Adapter or filesystem capability.

## Important limits

- The engineering path is production-wired, but no claim is made that all real
  Provider/model combinations have passed qualification. That requires valid
  user credentials and external network availability.
- Current durable routing supports one Provider across Reviewer roles because
  the current semantic runtime owns one Provider transport. The Shared contract
  rejects mixed-Provider routes rather than silently misrouting them.
- The settings surface currently exposes correctness Reviewer qualification and
  enable/disable. Security and fallback roles are supported by the durable
  contract/runtime but do not yet have a complete form workflow.
- v2.0 release certification still needs representative live-Provider and chaos
  campaigns, accessibility/four-locale end-to-end review, and signed installer/
  update verification. Those are release qualification, not missing authority
  boundaries in this slice.

## Suggested final v2.0 qualification sequence

1. Run the no-tool qualification and guarded semantic-review path against the
   supported representative Providers, recording timeout, malformed response,
   rate-limit and cost evidence without storing prompts or secrets.
2. Complete keyboard/screen-reader/four-locale end-to-end review of the settings
   and failure states; add security/fallback form controls only if required for
   the v2.0 supported configuration matrix.
3. With explicit signing/release authority, validate signed installation,
   update and rollback on clean Windows machines. Do not generate distribution
   artifacts before that authorization.
