# Pivot 宣传视频策略与制作执行书

> 版本：1.0  
> 适用产品版本：Pivot v0.1.33 起  
> 制定日期：2026-07-27  
> 发布平台：YouTube、哔哩哔哩、TikTok、抖音  
> 当前商业状态：全免费，不设置付费版、订阅版或“高级功能”暗示

## 1. 先做什么

不要试图用一条视频同时完成品牌介绍、功能教学和短视频传播。

首轮宣传应制作一个“母版内容包”，再剪成四类成片：

| 成片 | 时长 | 画幅 | 用途 |
|---|---:|---:|---|
| 品牌功能主片 | 75–90 秒 | 16:9 | YouTube、哔哩哔哩首发 |
| 完整功能演示 | 3–5 分钟 | 16:9 | 解释产品如何真正工作 |
| 三条竖屏短片 | 每条 20–35 秒 | 9:16 | TikTok、抖音、YouTube Shorts、B站竖屏 |
| 无声循环片段 | 6–10 秒 | 16:9 / 9:16 | 官网、动态、预热和更新公告 |

核心判断：

- 主片负责让人记住 Pivot。
- 完整演示负责建立可信度。
- 短片每条只证明一个价值点。
- 所有素材来自同一次真实、可重复的产品演示。
- 横屏版和竖屏版分别构图，禁止把横屏成片机械裁掉两边。

## 2. 宣传目标

### 2.1 第一目标

让第一次看到 Pivot 的人，在 15 秒内理解：

> Pivot 把一句任务变成可监督、可审查、可恢复的完整 AI 工作流程。

### 2.2 第二目标

证明 Pivot 不是概念演示。观众应真实看到：

1. 创建任务；
2. AI 制定计划；
3. 查看执行过程；
4. 检查文件和终端结果；
5. 逐块审查修改；
6. 通过检查点恢复；
7. 得到可交付成果。

### 2.3 长期品牌认知

Pivot 从软件开发工作开始，逐步成为统一的 AI 工作操作系统。未来通过免费插件扩展文档、研究、自动化、思维导图、幻灯片、图像和视频工作流。

长期愿景可以出现，但必须标注为“Roadmap / 规划中 / 插件生态方向”，不能伪装成已上线功能。

## 3. 受众

### 3.1 核心受众

- 正在使用 Codex CLI、Claude Code、Trae 等工具的开发者；
- 用 AI 独立制作产品的个人开发者和小团队；
- 希望知道 AI 做了什么、为何这样做、能否撤回的人；
- 需要同时管理模型、供应商、会话、终端和项目文件的高频用户。

### 3.2 扩展受众

- 未来希望用统一工作台完成研究、写作、自动化和内容生产的创作者；
- 对 Agent 感兴趣，但不愿接受黑箱执行的普通用户；
- 希望构建免费插件或接入本地工具的开发者。

## 4. 产品事实边界

### 4.1 首发视频可以直接演示

以下内容以当前仓库和 README 为依据，拍摄前仍需对发行构建做一次逐项验收：

- 持久会话、搜索、分组、标签、分叉、导出和删除恢复；
- 项目文件浏览、文件范围控制、快速打开和 `.gitignore` 处理；
- 对话驱动的安全 Agent 编辑；
- Hunk 级 Diff Review；
- 文件写入前后的检查点；
- 多终端；
- Plan → 审批 → 执行；
- Anthropic、OpenAI Compatible 等 BYOK Provider 配置；
- 本地加密保存密钥；
- 设置页、运行时和 CLI 维护入口；
- Outcome / Process / Engineering 三种信息深度所表达的统一任务状态。

### 4.2 拍摄前必须实测，不能只看界面

- Worker 是否真的执行，而不是静态状态演示；
- 测试、门禁和终端输出是否来自真实命令；
- 检查点能否成功恢复文件；
- Provider 切换是否不会闪烁或回退；
- CLI 不存在时是否显示友好状态，而不是 `ENOENT`；
- 新安装和无历史数据状态是否完整；
- 中英文界面是否没有缺失翻译；
- 视频中使用的功能是否已经进入当前发行构建。

### 4.3 只能作为未来愿景出现

- 官方文档工作室、幻灯片工作室、图像工作室、视频工作室；
- 完整插件市场和第三方 SDK；
- 云端长期托管、跨设备后台队列和移动审批；
- 尚未接通的远程 Agent、模型路由和自动化模板；
- 任何未通过真实端到端测试的 Figma 页面。

建议采用 80/20 原则：80% 画面证明现有能力，20% 结尾描述架构方向。

## 5. 创意概念

### 5.1 主题

中文主题：

> 从一句话，到可验证的交付。

英文主题：

> From intent to verifiable work.

### 5.2 创意机制：“沿轴推进”

“Pivot”既是转折点，也可以成为贯穿全片的视觉语言：

- 一条细轴从屏幕左侧延伸；
- 每个关键节点依次落在轴上：Task、Plan、Run、Review、Checkpoint、Artifact；
- 轴上的光点只在真实执行时使用青绿色；
- 需要用户判断时转为琥珀色；
- 风险和失败使用克制的低饱和红色；
- 最后多个工具窗口收拢到 Pivot 的一个任务视图中。

它能创造品牌记忆，又不会遮挡真实软件界面。

### 5.3 画面气质

延续 Pivot UI V2 的 Quiet Command Center：

- 石墨灰、暖灰、暖白为主体；
- 青绿色仅用于运行、成功和确认；
- 琥珀色用于需要关注的状态；
- 不使用紫色渐变、霓虹光、玻璃拟态和“AI 大脑粒子”；
- 动效短、稳、可解释，避免浮夸镜头旋转；
- 真实 UI 是主角，动效只帮助观众看懂状态变化。

### 5.4 声音气质

- 音乐：克制的电子脉冲与轻微机械节奏，不能像游戏预告片；
- 音效：任务建立、阶段推进、审批、Diff 接受、检查点恢复各有一个短提示音；
- 旁白：冷静、明确、有判断，不使用夸张销售语气；
- 不能为了节奏把终端输出配成虚假的“高速黑客”效果。

## 6. 90 秒品牌功能主片

### 6.1 演示任务

推荐使用一个准备好的公开示例项目：

> “检查登录模块，找出导致会话失效的问题，提出计划，修复代码，运行测试，并生成变更说明。”

这个任务同时具备：

- 普通人能理解的问题；
- 足够短的执行链；
- 文件、终端、计划、Diff、检查点和成果；
- 可预置稳定结果，避免录制时模型随机偏离。

演示项目必须使用自有或许可兼容的代码，不包含真实密钥、私人路径和客户数据。

### 6.2 分镜与旁白草案

| 时间 | 画面 | 旁白 / 屏幕文案 |
|---:|---|---|
| 0–3 秒 | 多个终端、聊天窗口、编辑器快速叠加；任务状态彼此割裂 | “当 AI 开始真正做事，答案已经不是最重要的部分。” |
| 3–8 秒 | 噪声收拢，进入 Pivot Now；一条轴线出现 | “你需要知道，它准备做什么，正在做什么，以及改了什么。” |
| 8–16 秒 | Command Dock 输入演示任务，创建 Task | “在 Pivot，一句话先成为任务。” |
| 16–27 秒 | Process 视图显示计划、阶段、权限和待确认项 | “计划、权限和执行阶段，都在同一条工作链上。” |
| 27–39 秒 | Agent 读取项目文件，终端运行测试，状态沿轴推进 | “文件、终端与 Agent 不再散落在不同工具里。” |
| 39–52 秒 | Engineering 视图定位变更；测试先失败后通过 | “每一步都有证据，失败也不会被藏起来。” |
| 52–65 秒 | Hunk Diff Review，逐块接受或拒绝 | “每一处修改都可以单独审查。” |
| 65–73 秒 | 展示 Checkpoint，并短暂演示恢复 | “每一个关键阶段，都能回到之前。” |
| 73–81 秒 | Outcome 视图展示完成状态、测试和变更摘要 | “最后得到的不是一段聊天，而是一份可验证的交付。” |
| 81–87 秒 | Provider、Runtime、Extensions 页面快切；未来插件图标以虚线框出现 | “从模型和运行时开始，Pivot 将通过免费插件连接更多工作。” |
| 87–90 秒 | Logo、主题句、CTA | “Pivot. From intent to verifiable work.” |

### 6.3 结尾 CTA

当前公开渠道尚未最终确认时，使用中性版本：

> Follow the build / 关注 Pivot 的构建进展

如果之后开放仓库：

> Try Pivot free · View on GitHub

禁止使用“免费试用”“解锁高级版”“限时免费”等与全免费策略冲突的词。

## 7. 三条短视频

### 7.1 短片 A：黑箱

主题：AI 最危险的不是改错，而是你不知道它改了什么。

- 0–2 秒：直接显示未经审查的大量修改；
- 2–7 秒：切到 Pivot Process，看到步骤和状态；
- 7–16 秒：切到 Hunk Diff Review；
- 16–24 秒：接受一块、拒绝一块；
- 24–30 秒：Checkpoint + “Review every change”。

中文标题建议：

> AI 改代码最危险的，不只是改错

英文标题建议：

> What did your coding agent actually change?

### 7.2 短片 B：一个任务，三种深度

主题：同一项工作，不同角色看不同深度。

- Outcome：只看结果和交付；
- Process：看步骤、权限和阻塞；
- Engineering：看文件、终端和 Diff；
- 三个视图连续切换，但任务进度保持不变。

屏幕主文案：

> One task. Three depths. One source of truth.

### 7.3 短片 C：可以回去

主题：AI 执行不应是不可逆的。

- 创建检查点；
- 执行修改；
- 测试失败；
- 一键回到检查点；
- 修正计划后重新执行。

屏幕主文案：

> Let agents move fast. Keep the work recoverable.

| 平台 | 用户意图 | 主内容 | 表达方式 | CTA |
|---|---|---|---|---|
| YouTube | 搜索工具、看完整评测 | 90 秒主片 + 3–5 分钟演示 + Shorts | 英文主旁白或英文字幕，技术证据充分 | GitHub、下载页、开发日志 |
| 哔哩哔哩 | 了解产品背景与开发过程 | 中文主片 + 完整演示 | 可增加 20–40 秒开发动机和真实踩坑 | 关注、评论、动态、仓库 |
| TikTok | 快速判断是否值得停留 | 20–35 秒单价值短片 | 前 1.5 秒直接给冲突，字幕优先 | Profile link、follow |
| 抖音 | 快速理解现实痛点 | 20–35 秒中文短片 | 少术语，多展示“改了什么、能否撤回” | 关注后续、主页了解 |

### 8.1 不做“一稿四投”

同一故事可以共用素材，但必须重新剪辑：

- YouTube / B站允许建立上下文；
- TikTok / 抖音先给结论和证据，再出现产品名；
- 短视频字幕必须烙印在画面中；
- 竖屏版一次只放一个主要 UI 区域；
- 重要按钮和字幕避开平台右侧按钮、底部说明和顶部标题区域。

## 9. 制作规格

以下是项目内部的交付标准，不等同于平台永久不变的上传上限。发布当天仍应检查各平台上传页。

### 9.1 横屏母版

- 分辨率：2560×1440 或 3840×2160；
- 画幅：16:9；
- 帧率：60 fps；
- 编码母版：高质量中间编码或高码率 H.264；
- 发布版：MP4 / H.264 / AAC；
- UI 录屏：至少 2560×1440、60 fps，系统缩放固定；
- 音频制作目标：约 -14 至 -12 LUFS Integrated，峰值不高于 -1 dBTP。

### 9.2 竖屏母版

- 分辨率：1080×1920；
- 画幅：9:16；
- 帧率：30 或 60 fps，全片统一；
- 时长目标：20–35 秒；
- 字幕字号以手机真机检查为准，正文不低于约 54 px；
- 字幕每屏不超过两行；
- UI 采用局部重排和放大，不能简单裁切。

### 9.3 字幕和语言

至少交付：

- 简体中文烙印字幕版；
- 英文烙印字幕版；
- 简体中文 `.srt`；
- 英文 `.srt`；
- 无字幕干净母版。

YouTube Shorts 当前支持最长 3 分钟的方形或竖屏视频，但本项目仍以 20–35 秒为首轮测试长度。超过 1 分钟的 Shorts 应格外检查音乐授权和 Content ID 风险。

## 11. 制作流程

### 阶段 A：产品验收

1. 建立视频专用演示项目；
2. 按分镜完整跑通一次；
3. 记录每一步实际耗时和不稳定点；
4. 修复会破坏演示的错误；
5. 冻结用于拍摄的构建版本。

验收不通过时不进入正式录制。

### 阶段 B：脚本锁定

1. 根据实测结果删去无法稳定展示的镜头；
2. 锁定 90 秒旁白；
3. 为每句旁白绑定真实画面；
4. 完成三条短片的独立开头；
5. 确定 CTA 和公开链接。

### 阶段 C：录屏

1. 关闭通知和无关后台程序；
2. 固定窗口尺寸、系统缩放、语言和主题；
3. 每个操作前后留出 1–2 秒剪辑余量；
4. 鼠标移动放慢，避免来回寻找；
5. 同一镜头至少录两遍；
6. 真实等待时间过长时可以合理压缩，但不可伪造执行结果。

### 阶段 D：后期

1. 先完成无音乐的故事粗剪；
2. 加入轴线、放大框和状态标记；
3. 录制旁白并按语义调整节奏；
4. 添加音乐和少量操作音效；
5. 制作字幕；
6. 从横屏素材重新编排竖屏版；
7. 输出平台版本。

### 阶段 E：质量检查

- 视频中的每个功能都能在同版本复现；
- UI 文案和旁白没有过时名称；
- 不出现旧版 Chat / IDE 二分叙事；
- 不把未来 Studio 或插件市场当作当前功能；
- 没有密钥、私人路径和第三方隐私信息；
- 字幕在手机上可读且未被平台控件遮挡；
- 无音乐版本也能看懂；
- 中英文术语一致；
- 音乐、字体、代码和素材授权可追溯；
- 上传为不公开/仅自己可见后完成一次平台端检查。

## 14. 衡量方式

首轮不以播放量单独判断成败，重点看：

- 前 3 秒继续观看比例；
- 15 秒留存；
- 主片平均观看时长；
- 封面点击率；
- 完整演示的章节跳转；
- 评论中是否有人能准确复述 Pivot 的价值；
- 主页、仓库或下载页点击；
- 用户最常追问的功能；
- 三条短片中哪个价值点最有效。

发布 7 天后做一次复盘：

1. 保留最有效的开头；
2. 删除观众误解最多的表述；
3. 把高频问题做成下一组短片；
4. 不因单条爆款盲目改变产品定位。

## 15. 不应该做的宣传片

- 先放 10 秒 Logo 再进入内容；
- 用大量 AI 粒子、机器人、大脑和代码雨代替产品；
- 从头到尾缩小展示整个桌面，导致手机上看不清；
- 按菜单逐项朗读功能；
- 展示不存在的“全自动完成一切”；
- 把规划中的插件工作室做成伪装的真实操作；
- 使用虚假终端输出或伪造测试通过；
- 四个平台上传完全相同的剪辑；
- 用“革命性、颠覆性、重新定义”等空泛词语；
- 让配乐、转场和动效抢走 UI 的注意力。

## 16. 如何让我直接开始制作

### 16.1 最简指令

### 16.2 开始前需要提供或确认

如果没有特别说明，我会采用括号内默认值：

## 18. 品牌表达档案

```text
VOICE PROFILE
=============
Author: Pivot 产品团队
Goal: 用可验证的产品证据说明 Pivot 如何让 AI 工作变得可监督、可审查、可恢复
Confidence: Medium-high

Source Set
- README.md — 当前已交付功能与使用方式
- 产品定位.md — 目标用户与产品定位
- 核心价值主张.md — 可见、可控、可信的价值基础
- docs/unified-work-model.md — Task / Run / Artifact / Review / Checkpoint 工作模型
- docs/free-ecosystem-policy.md — 全免费与插件生态政策
- Pivot UI V2-Figma AI设计总任务书.md — AI 工作操作系统与 Quiet Command Center 方向

Rhythm
- 中短句为主；关键判断单独成句
- 先给具体冲突，再展示产品证据，最后给愿景
- 不连续堆叠口号，不使用夸张排比

Opening Moves
- 从真实工作风险开始：改了什么、为何这样改、能否恢复
- 直接展示任务或失败状态，不用 Logo 开场

Endings
- 回到可验证的交付结果
- 使用明确 CTA：关注、查看仓库或试用当前版本

Vocabulary
- task, plan, run, review, checkpoint, artifact
- 任务、计划、执行、审查、检查点、成果
- visible, reviewable, recoverable, verifiable
- 可见、可审查、可恢复、可验证

Avoid
- 革命性、颠覆性、重新定义、全能、完全自动
- AI 大脑、魔法、秒速完成、解放生产力
- 免费试用、高级版、订阅解锁
- 未经证实的速度、准确率和兼容性数字

Rhetorical Devices
- 用同一任务在不同阶段的状态变化建立叙事
- 用“执行证据”回应“黑箱风险”
- 用检查点前后对照证明可恢复

Formatting
- 屏幕文案一屏一个判断
- 字幕每屏最多两行
- 产品术语中英文保持固定映射

Channel Notes
- X: 单一功能证据配短视频或 GIF，正文不超过一个核心判断
- LinkedIn: 强调可审查的 Agent 工作流和团队协作价值
- Email: 用版本事实、演示链接和明确更新内容，不写营销套话
```
